# 等结果：节奏、超时、失败、跨会话

## 一次提交是什么

`submit()` 建一个**任务组**（job），里面每条线路是一个**任务**（task）。任务组号形如 `u7f3a9c2b-261016-153000`，是取结果的唯一凭据；只能取自己账号下的。`submit()` 立即返回，不等运行。

## 大概要等多久

| 目标 | 通常 |
|---|---|
| `sim`、`<真机>-sim` | 几秒到一分钟（单条最长跑 60 秒，超时算失败） |
| `<真机>-sim-jiuding` | 空闲时要先启动，第一条可能等几分钟 |
| 真机 | 取决于排队：`qf devices` 的「排队」是前面还有多少条任务。2026-10 实测每条约 2–5 秒，排 100 条约等 5–10 分钟；真机还会不定时停下来校准，状态变成 `calibrating` 时只能等 |

告诉用户时给范围，不要给精确到分钟的承诺。

## 先短后长地等

`qf wait <号> --budget <秒>` 内部由 SDK 轮询（第一分钟每秒一次，之后每 5 秒，10 分钟后每 30 秒），到了预算就以**退出码 3** 返回并打印「完成几条 / 共几条」。你在对话里按这个节奏调用：

1. 提交后立刻 `--budget 60`；
2. 没好：告诉用户进度，`--budget 300`；
3. 还没好：`--budget 540`（别超过你所在工具的单条命令超时），可以再来一两次；
4. 累计 30 分钟左右还没好：停。告诉用户任务组号，说明「任务在平台上继续排队，之后回来让我取一下就行」。

能放后台的工具（Claude Code 的后台命令等）可以直接后台跑 `qf wait <号> --budget 7200`，完成后再分析，期间可以和用户聊别的。

用户中途说「不跑了」：`python -c "import quafu; print(quafu.job('<号>').cancel())"`。已经交给真机的任务只能停止等待，消耗的额度不退。

## 新会话里接着取

- 回到当初提交时的目录：`qf runs --refresh` 列出全部记录及最新状态，挑没取的 `qf wait <号>`、`qf analyze <号>`、`qf page <号>`。
- 不在那个目录、但有任务组号：`qf wait <号>` 照样能取，只是没有模板信息，分析按「通用分布对比」做（理想结果取自平台回传的线路）。
- 连号都没有：SDK 不提供「列出我的全部任务」；请用户到网站「我的任务」里找。

## 状态与失败

任务组状态：`Queued`（排队）、`Running`、`Finished`、`PartiallyFinished`（有成功有失败）、`Failed`、`Cancelled`。

| 现象 | 处理 |
|---|---|
| `PrecheckError`（提交时） | 线路或参数不合要求：比特数超限、shots 不是 1024 的倍数、用了真机不支持的东西。读错误信息改线路 |
| `DeviceUnavailable` | 目标不在线，换一台 |
| `QuotaError` | 到了每日硬上限，`retry_after` / `resets_at` 告诉你什么时候恢复（北京时间 23:00 重置）。超普通额度不会报错，只是排到最低优先级 |
| 某条任务 `Failed` | `qf wait` 会打印原因；`error.retryable` 为真时原样重交有意义 |
| `ServerUnavailable` | 平台暂时连不上，过一会儿再取；任务不会丢 |
| `JobNotFound` | 号写错了，或不是当前账号交的（换过账号？`python -m quafu whoami` 看看） |
